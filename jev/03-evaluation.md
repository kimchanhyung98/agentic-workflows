# Jev 공개 평가 검토와 실험 설계

> 확인일: 2026-09-22 · 아래 공개 수치는 공급자 게시 결과이며 재현하지 않음 · 자체 관측은 [Playground 실험](06-playground-experiment.md)·[100개 반복 실험](07-repeatability-experiment.md)

## 1. 공식 문서의 평가 예시를 읽는 기준

아래는 TypeSafe 공식 문서에 실린 평가 예시를 검토한 내용입니다. 공급자가 제시한 조건과 결과이며, 이 프로젝트에서 해당 평가를 재현한 것은 아닙니다. 자체 관측은 별도의 Playground·직접 HTTP 실험으로 구분합니다.

성능을 비교할 때는 입력 크기·질문 수·요청 묶음·실행 순서·모델 버전·보류 정책을 함께 확인해야 합니다. 특정 조건의 비용·시간 개선이나 반복 일치율을 일반 정확도·실제 업무 완료율로 해석하지 않습니다.

## 2. 한 요청의 여러 질문: 다른 비교 조건

공식 병렬 질문 cookbook은 53,777자 GDPR 문서에 13개 질문을 던집니다. Noul 8개·Choice 2개·Score 3개이며, `jev-1.12`에서 5회 반복한 공개 기록입니다. 모델 간 우열이 아니라 요청을 묶는 방식의 비교입니다. [Parallel questions](https://docs.typesafe.ai/cookbooks/parallel_questions)

| 공개 평균 | 묶어서 한 요청 | 질문별 13회 요청의 합 |
| --- | --- | --- |
| 비용 | $0.000497 | $0.006090 |
| 시간 | 0.27초 | 2.71초 |

공급자는 약 12.2배 비용 절감·10.0배 시간 개선으로 요약합니다. 같은 큰 상태를 반복 보내는 비용과 순차 요청의 시간을 줄이는 조건입니다. 13개 요청을 동시에 실행하는 기준선과의 비교는 아니므로 이를 동시 요청 대비 지연 개선으로 옮겨 쓸 수 없습니다. 일부 값에는 작은 변동도 있으며, 5회 반복은 완전한 결정성이나 현재 버전의 성능을 보장하지 않습니다. [실험 코드와 출력](https://docs.typesafe.ai/cookbooks/parallel_questions)

## 3. 높은 반복 일관성과 높은 정확도는 다르다

Choice 일관성 cookbook은 게시물 하나·8개 질문을 15회 평가한 2026-09-11의 `jev-latest` 기록입니다. 게시물·질문은 유지하지만 요청마다 다른 `uid`를 넣어, 바이트까지 동일한 입력의 반복 실험은 아닙니다. 최대 선택지 확률이 0.60 미만이면 보류하며, 이 기준은 `confidence`가 아닙니다. [Choice consistency](https://docs.typesafe.ai/cookbooks/consistency_choice_cookbook)

| Jev 공개 결과 | 의미 |
| --- | --- |
| 원시 선택 일치율 90.8% | 질문별 최빈 선택의 비율을 평균한 값 |
| 정책 적용 후 일치율 99.2% | 보류를 결정에 포함해 계산한 같은 지표 |
| 보류 25.8% | 자동 처리하지 않은 비중, 자동 처리 비중은 74.2% |

이는 모든 실행 쌍의 일치율이나 정답률이 아닙니다. 같은 오답·보류를 반복해도 높아질 수 있습니다. Haiku의 temperature 0 결과도 보류 없이 정책 일치율 100%이므로 Jev의 보편적 우위를 입증하지 않습니다. 별도 실험에서는 동일 입력의 변동과 무관한 필드 변경의 영향을 분리합니다. [공개 결과 표](https://docs.typesafe.ai/cookbooks/consistency_choice_cookbook)

## 4. 한국어 평가에서 확인할 것

공식 State 문서는 영어 중심 학습과 비영어, 특히 CJK에서의 정확도 저하 가능성을 안내합니다. 이는 한국어 업무 전체의 정확도 수치가 아니며, 단일 입력의 높은 확률도 일반 정확도를 증명하지 않습니다. [State](https://docs.typesafe.ai/concepts/state)

실제 한국어 평가에서는 반어·부정·존댓말·축약·문맥 누락·한영 혼용을 분리합니다. 확률 차이가 적절한 문맥 반응인지, 정답을 놓친 것인지 판정하려면 사람의 근거 있는 라벨과 반복 측정이 필요합니다.

## 5. 후속 실험 설계

아래는 본격적인 비교 평가의 설계안으로 아직 실행하지 않았습니다. 별도로 Playground 14회와 [고정 사례 100개의 직접 HTTP 10회 반복](07-repeatability-experiment.md)을 수행했지만, 사람 검수 정답셋·경쟁 모델·분리된 조정 데이터가 없는 합성 사례 실험입니다. 그 결과만으로 임계값과 목표 수치를 채택하지 않습니다.

### 과제와 기준선

| 과제 | 정답·판정 방식 | 비교할 실패 |
| --- | --- | --- |
| 고객 요청 분류 | 업무 담당자가 의도·정보 부족을 라벨링 | 오분류·누락된 선택지 |
| 긴급성·정책 해당 여부 | 명시적 기준과 근거 문장으로 판정 | 부정·반어·모호한 마감 표현 |
| 순서 있는 위험도 | 한 차원의 수준별 기준, 평가자 불일치 기록 | 경계 수준·다봉 분포·평균의 오해 |
| 후보 값 선택 | 원문 위치와 정답 후보 연결 | 후보 누락·잘못된 선택 |
| 추출 결과 검사 | 정답·오답 레코드를 분리 구성 | 오답 통과·정답의 불필요한 재처리 |

기준선은 규칙만 사용하는 처리, 구조화 출력 생성 모델, Jev입니다. 가능한 경우 같은 질문 분해와 같은 입력을 사용합니다. ‘단일 긴 프롬프트 대 분해된 workflow’ 비교는 모델 비교와 분리해 보고합니다.

고정 라벨 분류에는 SetFit, 경로 선택에는 Semantic Router를 선택적으로 추가합니다. 생성 후 검사 방식도 최종 결과와 전체 비용으로 평가하며, 모든 프로젝트에 동일한 API나 확률 출력이 있다고 가정하지 않습니다. [유사 프로젝트별 비교 단위](04-comparison.md)

### 데이터와 보류 정책

1. 평가할 업무 범위·정답 기준을 먼저 정하고, 평가자 사이의 불일치를 기록합니다.
2. 임계값을 정할 조정용 데이터와 최종 평가 데이터를 분리합니다. 유사 문장·같은 고객의 반복 기록이 양쪽에 섞이지 않게 합니다.
3. 언어·업무·난이도·발생 시점별 결과를 따로 봅니다. 모호한 사례를 억지로 하나의 확정 정답으로 만들지 않습니다.
4. Choice 확률, Noul 확률, Score 분포, `confidence`를 서로 다른 값으로 기록합니다.
5. 보류 비중과 자동 처리한 사례의 오류율을 함께 비교합니다. 사람 검토 시간과 상위 모델 비용도 포함합니다.

### 측정 지표

| 축 | 기록·계산할 내용 |
| --- | --- |
| 정확성 | 클래스별 오탐·누락, Score 수준 오차, 중요 오류 유형별 표본 수 |
| 확률 예측 품질 | Choice·Noul의 Brier score, 클래스별 결과와 산식 명시 |
| 확률 보정 | 확률 구간별 평균 예측·관측 빈도, 구간별 표본 수 |
| 보류 효과 | 자동 처리 비율에 따른 자동 처리 오류율, 보류 후 해결 시간 |
| 안정성 | 동일 입력 반복 일치율과 별도로 정답 일치율 기록 |
| 지연 | 단일·병렬·묶음 요청 각각 p50·p95, 재시도 포함·제외 구분 |
| 비용 | 입력 준비·모든 모델 호출·재시도·사람 검토를 합산 |
| 업무 결과 | 최종 완료·오실행·부분 완료·재작업, 올바른 완료 건당 비용 |

원시 기록에는 데이터셋 버전, 정답 작성 방식, 질문·기준, 요청 모델과 응답 모델, SDK 버전, 원시 응답·토큰 사용량, 실행 시각·지역·동시성·오류·재시도를 포함합니다. 고객 데이터는 별도 보관 정책을 정한 뒤 사용합니다.

Brier score는 확률 예측 품질의 지표로, 보정뿐 아니라 판별력과 데이터 불확실성도 반영합니다. 값이 낮아졌다는 이유만으로 RLCD의 보정 우위를 주장하지 않고 보정 곡선과 함께 해석합니다. [scikit-learn 확률 보정](https://scikit-learn.org/stable/modules/calibration.html)

### 비교 실험의 최소 완료 조건

- 모델·질문·데이터·정답 기준을 고정하고, 조정 데이터와 최종 평가 데이터가 분리돼 있어야 합니다.
- 성능 결과에는 표본 수·오류 사례·보류 비중을 함께 제시해야 합니다.
- 소규모 예시의 재실행, 더미 응답 검사, 전체 benchmark 재현을 서로 다르게 표시해야 합니다.
- 대체 경로 비용과 실패를 포함해야 하며, API 성공을 업무 완료로 대신 세지 않아야 합니다.

## 6. 현재 결론

공개 자료는 Jev의 계약과 평가 가능한 적용 패턴을 확인하는 데 충분합니다. [100개 반복 실험](07-repeatability-experiment.md)에서는 동일 요청 본문의 숫자 변동과 분류 변동을 구분했고, 직접 HTTP 클라이언트 시간·토큰·529 오류·재개를 기록했습니다. 다만 일반적인 한국어 정확도, 운영 지연 보장·총비용, 검증된 보류 정책의 오류율, 실제 업무 완료율은 검증하지 않았습니다.

다음 판단에 필요한 것은 추가 홍보 사례가 아니라, 좁게 정한 업무에서 사람의 정답·같은 비교 조건·실패 비용을 포함한 결과입니다. 비공개 학습 방법의 우열과 실제 제품의 업무 적합성은 끝까지 구분합니다.
