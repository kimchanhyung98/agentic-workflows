# Jev Playground 실제 실행과 결과 분석

> 실행일: 2026-09-22 16:07–16:15 KST · 실제 Playground 실행 14회 · 고유 가상 고객 문장 10개 · 응답 모델 `jev-1.13.0`

이 문서는 초기 소규모 실험의 당시 관측과 분석 결과를 정리합니다. 실험용 코드·테스트·입력 파일·화면 응답 기록은 저장소에서 제거했으며, 현재 문서만으로 원문 대조나 재집계는 할 수 없습니다. 이후 수행한 직접 HTTP 100개 × 10회와 정밀도·반복성·오류 분석은 [후속 보고서](07-repeatability-experiment.md)에 있습니다.

## 1. 이번에 확인한 것

로그인된 [TypeSafe Playground](https://console.typesafe.ai/playground)에서 고객 문의 분류를 실행했습니다. 가상 고객 입력을 사용했지만 모델 응답은 실제 서비스에서 받은 결과입니다.

작은 사례 집합에서 확인한 핵심은 다음과 같습니다.

1. 기준 사례 9개의 최초 결과에서 의도·오늘 마감 여부·가장 유력한 불만 수준이 작성자의 기대값과 일치했습니다. 일반적인 정확도나 한국어 품질을 입증하는 표본은 아닙니다.
2. 정보 부족을 높은 확신으로 판단할 수 있습니다. `unclear` 확률이 0.97이어도 처리에 필요한 정보가 생기는 것은 아닙니다.
3. Score의 평균과 가장 유력한 수준은 다를 수 있습니다. 직접 모욕 사례의 평균은 1.33인데 가장 유력한 수준은 2였고, confidence는 0이었습니다.
4. 같은 화면 입력을 반복해도 확률·점수가 조금 달라졌습니다. 단일 출력과 단일 confidence 기준만으로 운영 정책을 확정하면 안 됩니다.

이는 **소규모 실제 사용 실험**입니다. HTTP·SDK 직접 연동, 경쟁 모델 비교, 확률 보정 평가, 실제 환불·계정 변경, 운영 부하 시험은 수행하지 않았습니다.

## 2. 실험 과제와 고정 조건

과제는 고객 메시지 하나를 읽고 적절한 검토 경로를 정하는 것입니다. 환불 승인·중복 결제 사실 확인·계정 소유권 확인은 과제에 포함하지 않았습니다.

| 질문 | 타입 | 고정한 기준 |
| --- | --- | --- |
| `intent` | Choice | 환불·배송·계정·기타 명확한 요청·정보 부족의 5개 선택지 |
| `urgent_today` | Noul | 오늘 안에 처리하라는 명시적 요청인지 판단; ‘빨리’만으로 참이 아님 |
| `frustration` | Score | 0: 중립, 1: 모욕 없는 명시적 불만, 2: 직접 모욕 또는 위협 |

전체 질문과 문구는 실행 전에 고정했습니다. 입력은 문자열 State이며, 인용된 조작 지시를 실제 요청과 구분하도록 질문에 명시했습니다. 영어 고객 문장에도 동일한 한국어 질문·기준을 사용했으므로 전체 프롬프트 언어를 통제한 비교는 아닙니다.

첫 실행 전에 기준 사례 9개와 기대값을 정했습니다. 사람이 독립적으로 검수한 업무 정답셋은 아니며, 본 실험 작성자의 명시적 기준입니다. 한국어 모욕 결과를 관측한 뒤 영어 대응 사례를 추가하고 한국어 모욕을 두 번 더 실행했습니다. 질문·기준은 14회 동안 바꾸지 않았습니다.

| 단계 | 고유 사례·반복 | 완료 결과 수 |
| --- | --- | --- |
| 기준 실행 | 사전 작성한 9개 사례, 한국어 환불만 총 3회 | 11회 |
| 탐색적 후속 실행 | 영어 모욕 1회, 기존 한국어 모욕 추가 2회 | 3회 |
| 합계 | 고유 문장 10개, 실행당 질문 3개 | 14회·답 42개 |

반복 실행을 새 정답 표본으로 더하지 않습니다. 기준 사례의 27개 답 역시 서로 독립적인 고객 사례 27건이 아닙니다.

## 3. 브라우저 실행 과정과 기록 방식

1. 기존 Chrome 로그인 세션으로 Playground에 접근했습니다. `agent-browser` 자동 연결은 대상을 찾지 못했지만, Chrome의 네이티브 UI 제어로 화면 접근·실행이 가능했습니다.
2. 빈 State와 질문 영역에 더미 입력·고정 질문을 넣었습니다. 모델 선택은 화면의 `jev-latest`를 사용했고, 보존한 모든 결과의 `model`은 `jev-1.13.0`이었습니다. UI에서는 별칭 선택만 확인했으며 버전 ID를 고정한 실험으로 표현하지 않습니다.
3. 각 입력을 붙여 넣은 뒤 화면에서 전체 문장을 다시 읽어 확인하고 Run을 눌렀습니다. 편집 중 일부 문자 누락·입력 되돌림은 바로잡았으며, 확인되지 않은 편집 상태를 별도 결과로 세지 않았습니다.
4. 완료된 JSON 화면에서 `answers`, `usage`, `request_id`, `evaluation_time_ms`를 읽었습니다. 응답이 아직 준비되지 않은 경우 완료 화면을 다시 확인했으며 대기 상태를 결과로 만들지 않았습니다.
5. 14개의 서로 다른 요청 ID와 결과를 저장했습니다. 화면에서 모은 응답 배열과 저장 파일의 키 정렬 JSON 체크섬을 비교해 전사 일치를 확인했습니다. 이 체크섬은 복사 검사용이며 서버 출처를 암호학적으로 증명하지 않습니다.
6. 저장한 결과를 로컬 분석기로 재생해 기대값·반복 범위·토큰·분기 결과를 계산했습니다. 이 단계에서는 Jev를 다시 호출하지 않았습니다.

당시 수집한 자료는 접근성 트리로 읽은 **Playground JSON 표시값**이며 네트워크에서 받은 원시 HTTP 본문은 아닙니다. 화면 뒤의 재시도·캐시·추가 요청을 관측하지 않았으므로 ‘14회’는 완료 결과를 확인한 UI 실행 수입니다. API 키·로그인 자격 증명·실제 고객 데이터는 파일에 저장하지 않았습니다.

`started_at`·`observed_at`은 조작·관측 기록입니다. 화면을 읽고 기록하는 시간이 끼므로 둘의 차이를 요청 지연으로 계산하지 않습니다. `run-08`의 시작 시각은 보존하지 못해 `null`로 남겼습니다.

## 4. 기준 사례의 최초 결과

Noul은 설명용 집계에서 0.5 초과를 참, 미만을 거짓, 같으면 보류로 해석합니다. 운영용으로 보정한 임계값은 아닙니다. Score 수준은 평균을 반올림하지 않고 확률이 가장 높은 수준을 사용합니다. 동률이면 보류합니다.

| 사례·실행 ID | 사전 기대값: 의도 / 오늘 / 수준 | 실제 의도 | Noul | Score 평균 / 최빈 수준 / confidence |
| --- | --- | --- | --- | --- |
| 한국어 환불 `run-01` | refund / 참 / 1 | refund | 0.96 | 0.98 / 1 / 0.96 |
| 영어 환불 `run-04` | refund / 참 / 1 | refund | 0.94 | 0.99 / 1 / 0.98 |
| 환불·오늘 부정 `run-05` | account / 거짓 / 0 | account | 0.03 | 0.01 / 0 / 0.99 |
| ‘빨리’만 명시 `run-06` | account / 거짓 / 0 | account | 0.06 | 0.20 / 0 / 0.70 |
| 대상 정보 부족 `run-07` | unclear / 거짓 / 0 | unclear | 0.03 | 0.16 / 0 / 0.75 |
| 인용된 조작 지시 `run-08` | delivery / 거짓 / 0 | delivery | 0.12 | 0.04 / 0 / 0.94 |
| 한국어 직접 모욕 `run-09` | account / 참 / 2 | account | 0.87 | 1.33 / 2 / 0.00 |
| 내일 배송 답변 `run-10` | delivery / 거짓 / 0 | delivery | 0.03 | 0.01 / 0 / 0.99 |
| 상담 시간 문의 `run-11` | other / 거짓 / 0 | other | 0.03 | 0.00 / 0 / 1.00 |

위 해석으로 Choice 선택값·Noul 이진 판단·Score 최빈 수준은 각각 9/9 일치했습니다. 반면 Score 평균을 정수로 반올림하면 모욕 사례를 수준 1로 바꾸므로 8/9입니다. 이는 모델을 바꾸지 않아도 애플리케이션의 출력 해석이 결과를 바꿀 수 있음을 보여줍니다. 평균 점수가 틀렸다고 결론내리는 비교는 아닙니다.

### 정보 부족과 높은 confidence

“그거 좀 바꿔 주세요.”는 `unclear` 확률 0.97, `other` 0.03, Choice confidence 0.96이었습니다. 이 출력은 ‘무엇을 바꿀지 모른다’는 판단에 가깝습니다. 확신이 높다는 이유로 임의의 계정·배송 변경을 실행하면 안 됩니다. 당시 설명용 정책에서는 confidence 검사보다 정보 부족 분기를 먼저 적용했습니다.

### 부정·기한·인용문

환불을 원하지 않고 오늘 처리할 필요도 없다는 문장은 `account`, Noul 0.03이었습니다. ‘빨리 부탁’만 있는 문장은 Noul 0.06으로, 오늘 마감을 명시한 환불 문장과 구분했습니다. 다만 마감 표현·반어·복합 의도 전체를 검증한 것은 아닙니다.

인용된 조작 지시가 있는 문장은 `delivery`, Noul 0.12, Score 0.04였습니다. **인용문이라고 명확히 표시한 단일 사례**에서 실제 요청을 구분한 결과입니다. 질문에도 인용문 제외 기준이 있으므로, 무표식 공격·다중 문서·권한 탈취 전반에 대한 주입 공격 저항으로 일반화하지 않습니다.

## 5. 반복과 영어 대응 사례에서 드러난 Score 해석

한국어 모욕 문장은 “너희는 멍청하다. 로그인 비밀번호를 오늘 안에 재설정해 줘.”이며, 탐색적 영어 문장은 “You are stupid. Reset my login password by the end of today.”입니다.

| 실행 | 언어·단계 | Score | P(0) | P(1) | P(2) | confidence |
| --- | --- | --- | --- | --- | --- | --- |
| `run-09` | 한국어·기준 | 1.33 | 0.32 | 0.02 | 0.66 | 0.00 |
| `run-12` | 영어·추가 | 1.32 | 0.33 | 0.03 | 0.64 | 0.00 |
| `run-13` | 한국어·추가 반복 | 1.45 | 0.26 | 0.02 | 0.72 | 0.18 |
| `run-14` | 한국어·추가 반복 | 1.35 | 0.32 | 0.02 | 0.66 | 0.02 |

네 번 모두 최빈 수준은 2지만, 평균은 1.32–1.45여서 반올림하면 1입니다. 중간 수준 1의 확률은 0.02–0.03에 불과합니다. 따라서 평균만 보면 ‘보통 불만’처럼 보이지만, 분포는 중립과 모욕에 나뉘어 있습니다. Score가 가중평균이라는 계약과 일치하는 해석이며, confidence를 단순한 ‘가장 유력한 수준의 확률’로 읽어서도 안 됩니다. [Score 의미](https://docs.typesafe.ai/primitives/score), [confidence 설명](https://docs.typesafe.ai/confidence)

영어 대응 문장에서도 유사한 분포가 관측됐으므로 한국어 문제만으로 원인을 단정할 수 없습니다. 그렇다고 언어 간 품질이 같다는 증거도 아닙니다. 가능한 후속 확인은 단일 차원의 기준을 더 명확히 작성한 별도 실험, 여러 모욕·중립 표현, 평가자 라벨 검토입니다. 이번 기록의 질문을 사후 수정해 결과를 대체하지 않았습니다.

한국어 환불의 3회 반복은 의도가 모두 `refund`였고 Noul 0.94–0.96, Score 0.97–0.98, Score confidence 0.95–0.97이었습니다. 한국어 모욕의 3회는 Noul 0.87–0.88, Score 1.33–1.45, confidence 0.00–0.18이었습니다. 이는 같은 화면 입력의 관측 범위일 뿐, 바이트까지 동일한 HTTP 요청의 반복이나 변동 원인 검증은 아닙니다.

### 표시 정밀도의 한계

표시 확률로 다시 계산한 평균과 표시 Score에는 최대 약 0.01 차이가 있습니다. 예를 들어 `run-09`는 `0×0.32 + 1×0.02 + 2×0.66 = 1.34`인데 표시 Score는 1.33입니다. `run-05`에서는 P(0)이 1, 나머지가 0으로 표시되지만 Score는 0.01입니다.

화면 값만으로 서버 계산 오류를 주장하지 않습니다. 원시 값의 자릿수, 서버·클라이언트 중 어디서 반올림됐는지 확인하지 못했습니다. 당시 로컬 분석에서는 이 차이를 임의 보정하지 않고, 각 값이 소수 둘째 자리로 반올림됐다는 가정 아래의 허용범위를 별도 검사했습니다. 직접 API 응답의 정밀도에 대한 후속 관측은 [반복 실험 보고서](07-repeatability-experiment.md)에 정리했습니다.

## 6. 시간·토큰·참고 비용

아래는 당시 수집한 14개 JSON의 집계입니다. `evaluation_time_ms`는 서비스가 화면 JSON에 보고한 필드이며 브라우저 전체 왕복 시간은 아닙니다.

| 항목 | 관측값 |
| --- | --- |
| 완료 UI 실행 / 서로 다른 요청 ID | 14 / 14 |
| 반환 모델 | 모두 `jev-1.13.0` |
| 입력 / 출력 토큰 합계 | 9,858 / 1,205 |
| `evaluation_time_ms` 최소 / 중앙 / 최대 | 59.54 / 110.90 / 256.14 ms |
| 실제 청구 금액 | 확인하지 않음 |

소표본·단일 세션이며 동시성·부하·재시도를 통제하지 않았습니다. 따라서 p95·SLO·한국 지역 네트워크 지연이나 경쟁 모델 대비 속도 개선을 주장하지 않습니다. UI의 `87ms + 208ms` 같은 추가 시간 표시는 일부 기록했지만 두 번째 값의 정의를 확인하지 못해 네트워크 시간으로 합산하지 않았습니다.

확인일의 공개 입력 단가 $0.042/100만 토큰과 출력 무료 조건을 단순 적용하면 `9,858 × 0.042 / 1,000,000 = $0.000414036`입니다. 이는 **공개 단가 기준 참고 계산**이지 청구 내역이 아닙니다. Playground 과금 여부·크레딧·할인·관측하지 못한 내부 요청은 확인하지 않았습니다. [공식 Models 가격](https://docs.typesafe.ai/models)

## 7. 설명용 처리 흐름

실험 당시 로컬 분석에서 실제 응답을 설명용 정책에 적용해 문의 처리 경로를 확인했습니다. 외부 큐 전송이나 환불·계정 조작은 하지 않았습니다.

| 관측 결과 | 설명용 로컬 분기 | 확인한 경계 |
| --- | --- | --- |
| `unclear`, confidence 0.96 | 추가 정보 요청 | 높은 확신과 충분한 정보는 다름 |
| 모욕 사례의 낮은 Score confidence | 사람 검토 | 평균·최빈 수준·불확실성을 구분 |
| `refund` | 환불 검토 큐 | 의도 분류가 환불 승인 권한은 아님 |
| 나머지 명확한 문의 | 해당 문의 큐 | 실제 업무는 별도 시스템에서 처리 |

Score confidence 0.5라는 검토 기준은 결과 관측 후 만든 설명용 값입니다. 이번 작은 사례에서 맞아 보인다는 이유로 운영 기준으로 채택하지 않습니다. 긴급성은 참고 정보일 뿐 권한을 부여하지 않았으며, 실제 업무를 실행하거나 환불을 승인한 경로는 없었습니다.

## 8. 다음 평가에서 해소할 질문

이번 실험으로 출력 형식과 중요한 해석상의 함정을 실제 결과에 연결했습니다. 도입 판단에는 다음 증거가 더 필요합니다.

- 기준 검토: 업무 담당자의 라벨, 모욕·불만의 경계, 모호한 사례의 평가자 불일치를 기록합니다.
- 한국어 확장: 반어·존댓말·축약·복합 요청·긴 문맥·실제 빈도에 맞는 중립 사례를 포함합니다.
- 계약 확인: 버전을 고정한 직접 HTTP·SDK 실행으로 원시 정밀도·오류·재시도·전체 왕복 시간을 확보합니다.
- 정책 평가: 조정용·평가용 데이터를 분리해 검토 임계값별 오류와 보류 비중을 비교합니다.
- 대안 비교: 같은 입력·라벨로 규칙, 구조화 출력 모델, 필요한 경우 SetFit·의미 라우터를 비교합니다. 이번에는 대안 프로젝트를 실행하지 않았습니다.

평가 완료 조건은 [실험 설계](03-evaluation.md), 각 대안의 역할 차이는 [유사 프로젝트 비교](04-comparison.md)에 정리했습니다.
