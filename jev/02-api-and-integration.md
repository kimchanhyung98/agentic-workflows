# Jev API·SDK와 적용 패턴

> 확인일: 2026-09-22 · 공식 HTTP 문서 기준 · 직접 HTTP 실행은 [반복 실험](07-repeatability-experiment.md) · SDK 실행 미수행

## 1. 요청의 기본 단위

HTTP 엔드포인트는 `POST https://api.typesafe.ai/v1/systemone`이며 Bearer 인증을 사용합니다. 요청의 핵심은 `model`, `state`, `questions`입니다. 질문 맵의 키는 응답을 연결하는 식별자이며 모델에 전달되지 않습니다. `is_urgent` 같은 키에만 질문의 의미를 넣지 말고 `instructions`에 명시해야 합니다. [API reference](https://docs.typesafe.ai/api)

다음은 환불 의도와 긴급성을 분리하는 본 문서의 작성 예시입니다. 계약을 설명하기 위한 JSON이며 실제 응답이나 효과를 검증한 예제가 아닙니다.

```json
{
  "model": "jev-1.13.0",
  "state": {
    "customer_message": "결제가 두 번 됐어요. 하나만 취소해 주세요. 오늘 해결이 필요합니다."
  },
  "questions": {
    "intent": {
      "type": "choice",
      "instructions": "고객이 요청한 주된 처리를 선택하세요.",
      "criteria": {
        "refund": "중복 결제 취소 또는 결제 금액 반환을 요청함",
        "other": "환불이나 결제 취소가 아닌 요청",
        "unclear": "요청한 처리를 판단할 정보가 부족함"
      }
    },
    "urgent": {
      "type": "noul",
      "instructions": "고객이 오늘 안에 해결해 달라는 요구를 명시했는가?"
    }
  }
}
```

이 요청은 환불 가능 여부·중복 결제 사실·실제 취소 권한을 판정하지 않습니다. 그런 사실과 정책은 주문·결제 데이터 및 코드로 별도 확인해야 합니다.

### 응답에서 업무 분기로 연결하기

아래는 앞선 요청과 연결한 설명용 가상 응답입니다. 확률·confidence·토큰 수는 실제 측정값이 아니며, 이 값에서 confidence 계산식을 유도하면 안 됩니다. 필드 구조는 [HTTP 응답 계약](https://docs.typesafe.ai/api)을 따릅니다.

```json
{
  "model": "jev-1.13.0",
  "answers": {
    "intent": {
      "type": "choice",
      "choice": "refund",
      "probabilities": { "refund": 0.88, "other": 0.12, "unclear": 0.0 },
      "confidence": 0.81
    },
    "urgent": { "type": "noul", "noul": 0.95 }
  },
  "usage": { "input_tokens": 300, "output_tokens": 40 }
}
```

애플리케이션은 `answers.intent`와 `answers.urgent`를 요청 ID에 연결합니다. 다음 순서는 본 문서의 정책 예시이며, 임계값이나 자동 환불 정책을 채택한 것이 아닙니다.

| 순서 | 확인할 조건 | 이 사례의 처리 |
| --- | --- | --- |
| 1. 계약 확인 | 필요한 답·타입·선택지·확률 범위가 정상인가? | 누락·오류 응답이면 판단을 업무 실행에 쓰지 않음 |
| 2. 정보 부족 | `unclear`가 선택되거나 필요한 결제 정보가 없는가? | 시스템에서 조회하고, 여전히 부족하면 추가 정보 요청 |
| 3. 판단 보류 | 선택 확률 또는 confidence가 사전에 검증한 기준에 미달하는가? | 사람이 분류하거나 추가 문맥으로 다시 판단 |
| 4. 업무 분기 | 환불 의도로 분류됐는가? | 환불 검토 경로로 전달, 실제 중복 결제 여부는 별도 조회 |
| 5. 우선순위 | Noul이 검증한 긴급성 기준을 충족하는가? | 검토 우선순위에만 반영, 승인 권한으로 사용하지 않음 |
| 6. 실행·완료 | 권한·정책·필요한 승인이 확인됐는가? | 승인된 취소만 수행하고 결제 시스템의 최종 상태 확인 |

따라서 이 가상 응답만으로 ‘환불 완료’라고 결론낼 수 없습니다. `unclear`는 선택지의 내용이고, 보류는 애플리케이션의 행동이라는 차이도 유지합니다. [전체 실행 흐름](00-diagram.md)

## 2. 세 가지 결과를 읽는 방법

| 타입 | 주요 결과 | 해석 |
| --- | --- | --- |
| Choice | `choice`, `probabilities`, `confidence` | 주어진 선택지의 확률 분포와 선택 결과 |
| Score | `score`, `probabilities`, `confidence`, `legend` | 순서 있는 수준별 분포와 그 가중평균 |
| Noul | `noul` | 명제가 참일 확률, 0–1 |

Choice는 제공한 선택지 사이의 판단입니다. 빠진 업무 상태를 발견하는 장치로 대신 쓰지 않습니다. 선택지에 정보 부족을 넣는 것과 낮은 확신 때문에 코드에서 보류하는 정책은 별개로 평가합니다. [Choice](https://docs.typesafe.ai/primitives/choice)

Score는 2–10개 수준의 인덱스 `0 … K-1`에 확률을 곱해 더한 값입니다. 예를 들어 확률이 `[0.2, 0.3, 0.5]`이면 점수는 `0×0.2 + 1×0.3 + 2×0.5 = 1.3`입니다. 가장 유력한 등급이나 정수 등급을 그대로 반환하는 것이 아닙니다. 각 기준은 한 차원에서 독립적으로 이해할 수 있게 작성합니다. [Score](https://docs.typesafe.ai/primitives/score)

본 문서의 해석 예로 `[0.5, 0, 0.5]`와 `[0, 1, 0]`은 점수가 모두 1이지만 분포가 다릅니다. 평균 점수만으로 모호함을 판단하지 말고 원시 분포도 기록합니다.

실제 Playground의 모욕 사례에서도 Score 평균 1.33과 최빈 수준 2가 달랐습니다. [후속 직접 HTTP 실험](07-repeatability-experiment.md)에서도 반환 확률의 가중합과 Score에 최대 약 0.01 차이가 있었고, 일부 분포의 합은 0.99였습니다. 숫자는 모두 0.01 단위였으므로 UI만의 표시 문제로 설명하지 않으며, 내부 정밀도·반올림 위치는 미확인입니다. 당시 분석에서는 원문 값을 임의 보정하지 않았습니다.

Noul의 0.05는 ‘낮은 확신’이 아니라 해당 명제가 거짓일 가능성이 높다는 의미입니다. 0.5 근처가 애매한 판단에 해당합니다. 승인·거절·보류의 경계는 업무 오류 비용을 고려해 별도로 정합니다. [Noul](https://docs.typesafe.ai/primitives/noul)

## 3. 병렬 질문의 경계

같은 상태를 읽는 서로 독립적인 질문은 한 요청으로 묶을 수 있습니다. 필요할 수 있는 판단을 미리 요청한 뒤 코드에서 필요한 결과만 사용하는 패턴도 공식 문서에 있습니다. 다만 사용하지 않은 질문의 비용도 평가에 포함해야 합니다. [Fan-out](https://docs.typesafe.ai/patterns/fan-out)

아래 구분은 적용 시의 설계 원칙입니다.

- 함께 물을 수 있음: 같은 고객 메시지의 의도·긴급성·정책 관련성.
- 후속 호출이 필요함: 앞선 답에 따라 가져올 문서가 달라지거나, 실행 뒤 화면·업무 상태가 바뀌는 경우.
- 별도 코드 검사가 필요함: 두 답이 동시에 참이면 안 되는 조건, 권한·한도·합계 등 확정적 규칙.

## 4. 한도·오류·연동 시 확인할 조건

| 항목 | 확인한 값·조건 |
| --- | --- |
| 가격 | 입력 100만 토큰당 $0.042, 출력 무료 |
| 입력 크기 | 상태 + 모든 질문 총합 64k 토큰, 상태 + 가장 긴 질문 32k 토큰 |
| 처리 제한 | 초당 250,000 토큰, 분당 1,200 요청으로 기재 |
| 모델 고정 | 직접 HTTP 반복 실험은 `jev-1.13.0` 명시·응답 버전 확인; 이전 Playground는 별칭 사용 |

위 값은 열람 시점의 [Models](https://docs.typesafe.ai/models) 명세이며 서비스 지연 보장이 아닙니다. 별칭은 이후 다른 버전을 가리킬 수 있습니다.

API 문서는 401 인증 오류, 422 검증 오류, 429 속도 제한, 529 과부하를 설명합니다. 응답에는 `answers`와 입력·출력 토큰 사용량이 포함됩니다. 원인에 맞게 오류를 분류하고 재시도 비용도 집계해야 합니다. [API reference](https://docs.typesafe.ai/api)

공식 API 문서는 429·529 오류에 지수 backoff를 적용하며, 기본 재시도 정책을 쓰는 SDK는 이를 자동 처리한다고 안내합니다. SDK의 제한 시간·재시도 횟수·전체 대기 시간은 실제 연동 전에 사용하는 버전에서 확인해야 합니다. 이 문서에서는 SDK를 실행해 검증하지 않았습니다. [오류 처리 안내](https://docs.typesafe.ai/api)

### 공식 문서 사이의 확인 과제

| 항목 | 자료 사이의 차이 | 현재 문서의 취급 |
| --- | --- | --- |
| `null` 입력 | Advanced는 instructions·Score 수준의 null 허용, HTTP 스키마 표기는 더 좁음 | 서버 수용 여부 미확인, null에 의존하지 않음 |
| Score `legend` | HTTP 표기는 문자열 값, Advanced는 구조화된 Score 수준도 설명 | 선택한 표현의 실제 응답을 통합 단계에서 확인 |

이는 문서 표기의 차이이지 서버 오류를 재현한 결과가 아닙니다. [API](https://docs.typesafe.ai/api), [Advanced structure](https://docs.typesafe.ai/primitives/advanced)

## 5. 공식 cookbook에서 얻는 적용 패턴

### 후보 추출은 코드, 선택은 모델

공식 값 추출 예제는 정규식으로 후보를 넓게 찾고 Choice로 선택한 다음 원문 값을 복사하는 방식입니다. 숫자를 자유 생성하지 않게 만들 수 있지만, 잘못된 후보를 선택하거나 후보 추출 단계에서 정답을 놓칠 위험은 남습니다. [Pre-parsed value extraction](https://docs.typesafe.ai/cookbooks/pre_parsed_value_extraction_cookbook)

이 프로젝트에 적용한다면 후보별 원문 위치와 식별자를 보존하고, 선택 결과를 원문에 대응시켜 값·형식을 코드로 검증하는 방식이 후보입니다. 이는 아직 구현하지 않은 제안입니다.

### 생성 모델의 결과를 검사하고 필요할 때 상위 모델로 전환

SDE(Structured Data Extraction, 구조화 데이터 추출) cascade 예제는 작은 생성 모델의 추출 → 필드별 Jev 검사 → 필요시 강한 모델 호출을 설명합니다. 중요한 제한은 설명용 실행에서 재현성을 위해 오류가 있는 추출 레코드를 고정한다는 점입니다. 공개된 100개 프롬프트 그래프도 공급자의 내부 결과이며 이 저장소의 실험이 아닙니다. [SDE cascade](https://docs.typesafe.ai/cookbooks/sde_cascade)

검사 모델도 틀릴 수 있습니다. 따라서 후속 평가에서는 ‘생성 모델 오류를 Jev가 통과시킨 비율’과 ‘맞는 결과를 불필요하게 상위 모델로 보낸 비율’을 함께 측정합니다. 높은 확률의 검사를 통과했다는 이유만으로 실행 권한을 자동 부여하지 않습니다.
