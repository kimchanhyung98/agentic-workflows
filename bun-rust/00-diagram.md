# Bun Rust 포팅 아키텍처와 실행 다이어그램

이 문서는 두 종류의 흐름을 함께 보여준다.

- **관찰:** Bun 공식 회고, 병합 PR, 공개 workflow에서 확인한 실행 방식
- **권장:** 공개 자료에 빠진 재시작, 충돌 방지, 완료 판정을 보완한 범용 설계

둘을 구분하지 않으면 Bun이 실제로 사용한 장치와 다른 프로젝트에 필요한 보강책이 섞인다.

## 1. 전체 포팅 단계

```mermaid
flowchart TD
    A["관찰 · 기존 동작 기준선<br/>TypeScript 테스트 스위트"] --> B["관찰 · 포팅 계약<br/>PORTING.md · LIFETIMES.tsv"]
    B --> C["관찰 · 3파일 파일럿<br/>파일별 구현 1 · 리뷰 2 · 수정 1"]
    C --> D{"파일럿 통과?"}
    D -- "아니요" --> B
    D -- "예" --> E["관찰 · 기계적 전체 포트<br/>워크플로 샤드 4개 · 워크트리 4개"]
    E --> F["관찰 · crate 경계와 순환 의존 정리<br/>약 100개 crate가 목표"]
    F --> G["관찰 · 컴파일 오류 큐<br/>약 16,000개 오류에서 시작"]
    G --> H["관찰 · 링크 · 시작 · CLI<br/>bun --version → 개별 명령"]
    H --> I["관찰 · 로컬 테스트 실패 큐<br/>폴더 기준 4-shard"]
    I --> J["관찰 · 6개 플랫폼 CI<br/>실패 파일 972 → 23 → 0"]
    J --> K{"전 플랫폼 100%?<br/>skip · 삭제 0?"}
    K -- "아니요" --> J
    K -- "예" --> L["관찰 · 수동 확인 후 main 병합"]
    L --> M["관찰 · canary<br/>보안 리뷰 · Miri CI 확대 · 24/7 퍼징"]
    M --> N["예고 · v1.4 안정판"]
```

`main` 병합은 출시와 같은 사건이 아니다. 조사 기준일인 2026-07-26 현재 Rust 구현은 `main`과 canary에 있고, 최신 안정
태그 v1.3.14는 Zig 구현이다.

## 2. 한 작업을 처리하는 역할 셀

공식 회고는 구현자와 리뷰어에게 서로 독립된 컨텍스트를 주었다고 설명한다. 리뷰어는 구현 과정의 대화를 보지 않고 diff만
받으며, 변경이 잘못됐다는 전제에서 문제를 찾는다.

```mermaid
flowchart TD
    O["관찰 · 오케스트레이터<br/>입력 · 규칙 · 배정 범위 고정"] --> I["관찰 · 구현자 1<br/>포트 또는 수정안 작성"]
    I --> P["제안 diff"]
    P --> R1["관찰 · 리뷰어 A<br/>독립 컨텍스트"]
    P --> R2["관찰 · 리뷰어 B<br/>독립 컨텍스트"]
    R1 --> V{"두 리뷰 결과"}
    R2 --> V
    V -- "수정 필요" --> F["관찰 · 수정자 1<br/>지적 재현 · 수정"]
    F --> P2["권장 · 수정안 재제출"]
    P2 --> R1
    P2 --> R2
    V -- "차단 지적 없음" --> C["승인된 제안"]
    C --> G["권장 · 통합자<br/>입력·규칙·패치 해시 확인 · 직렬 적용"]
    G --> A["권장 · 기준 검증"]
```

여기서 `1-2-1`은 제품 코드의 영구 조직도가 아니라 한 작업의 검증 셀이다. 병합 커밋에 남은 개별 workflow 중에는 리뷰어
수가 하나인 변형도 있다. 모든 줄을 두 번 리뷰했다는 내용은 공식 회고의 집계이며, 공개 코드만으로 각 줄의 리뷰 원장을
재구성할 수는 없다. 수정본을 다시 리뷰하고 한 통합자만 적용하게 하는 마지막 두 계약은 공개 기록의 빈틈을 보완한 권장
설계다.

## 3. 컴파일 오류 목록을 작업 큐로 쓰는 법

오류 큐의 권장 수명은 한 검증 라운드, 즉 한 `epoch`이다. 컴파일 결과가 나온 commit과 규칙 버전을 함께 고정하고, 통합이
끝날 때까지 목록을 바꾸지 않는다.

```mermaid
flowchart TD
    S["권장 · 기준 커밋 Sₖ"] --> C["cargo check 1회<br/>JSON 진단 수집"]
    C --> N["정규화 · 진단 식별자<br/>crate · 파일 · 원인별 그룹"]
    N --> M["불변 작업 명세<br/>epoch k"]
    M --> D["결정적 샤드 배정<br/>겹치지 않는 쓰기 리소스"]
    D --> W1["작업자 0"]
    D --> W2["작업자 1"]
    D --> W3["작업자 N"]
    W1 --> R["독립 리뷰 · 수정"]
    W2 --> R
    W3 --> R
    R --> B["통합 장벽<br/>통합자만 적용"]
    B --> S2["새 commit Sₖ₊₁"]
    S2 --> C2["cargo check 재실행"]
    C2 --> Q{"오류 0?"}
    Q -- "아니요" --> X["epoch k 종료<br/>k ← k+1"]
    X --> N
    Q -- "예" --> L["cargo build · 링크 단계"]
```

작업자가 `done`을 썼다고 끝난 것이 아니다. 새 기준 커밋에서 검증을 다시 실행했을 때 해당 진단이 나타나지 않아야 한다.
한 오류를 고치면서 뒤의 오류가 함께 사라지거나 새 오류가 드러날 수 있기 때문이다.

공개된 Bun `phase-d-build-queue`와 `phase-d-crate-shard`도 먼저 빌드 결과를 파일별 작업으로 고정한 뒤 작업자에게
배분한다. 권장 설계에서는 텍스트 grep보다 Cargo의 `--message-format=json`을 사용해 진단 구조를 보존한다.

## 4. 단계별 샤드 경계

단계가 바뀌면 샤드 키도 바뀐다. 각 검증 도구가 독립적으로 판단할 수 있는 작업 단위에 맞춘다.

| 단계 | 관찰된 주 샤드 키 | 공개 workflow의 배정 범위 | 전역 동기화 지점 |
|---|---|---|---|
| 수명 분류 | Zig 파일·필드 | 분류 레코드 | `LIFETIMES.tsv` 검토 |
| 기계적 포트 | 원본 Zig 파일 → Rust 파일 | 고정된 대상 파일 | 파일 포트 완료 후 |
| 컴파일 복구 | crate → 진단 파일 | 주 배정 파일, 일부 변형은 같은 소스 디렉터리의 추가 파일 허용 | crate별 `cargo check` 재실행 |
| 로컬 테스트 | 테스트 폴더·파일 | 실패 원인을 고치는 관련 코드 | 테스트 묶음 재실행 |
| CI 복구 | 플랫폼·실패 원인 시그니처 | 원인별 관련 코드 | CI 전체 재실행 |
| main 추종 | 분기 기준점 이후 커밋 | 동등 변경 또는 제외 결정 | main 동등성 검증 |

```mermaid
flowchart LR
    P["포트 단계<br/>파일"] --> C["컴파일 단계<br/>crate → 파일"]
    C --> T["로컬 테스트<br/>폴더 → 테스트"]
    T --> CI["CI<br/>플랫폼 → 원인 시그니처"]
    CI --> MP["main 추종<br/>커밋"]
```

Bun의 4개 worktree는 샤딩·격리 단위였고, 최대 약 64개의 Claude 세션은 그 안의 작업자였다. 세션마다 worktree를 만들면 디스크
비용이 커지고 서로의 변경을 통합하기 어렵다. 반대로 여러 작업자가 같은 파일을 쓰면 충돌과 덮어쓰기가 생긴다. 따라서
권장 설계에서는 `worktree 수 = 작업자 수`로 가정하지 않고, 각 epoch의 샤드 작업 명세가 단일 작성자를 보장해야 한다.

공개된 crate shard workflow는 오류가 80개를 넘으면 약 800줄 구간으로 나누는 변형도 사용한다. 같은 파일의 구간별 수정이
서로 영향을 주지 않는다는 증거가 없다면 이 방식은 그대로 복제하지 않는 편이 안전하다.

## 5. 권장 검증 사다리

`cargo check` 성공만으로 포트가 끝나지 않는다. Cargo 문서도 `check`가 최종 codegen을 생략하므로 일부 진단은 놓칠 수
있다고 설명한다.

```mermaid
flowchart TD
    A["1 · cargo check<br/>crate · workspace"] --> B["2 · cargo build<br/>debug · release"]
    B --> C["3 · 링크 · 프로세스 시작"]
    C --> D["4 · 최소 CLI<br/>--version · 단일 명령"]
    D --> E["5 · 기존 테스트<br/>차등 결과 비교"]
    E --> F["6 · 무거운 테스트<br/>누수 · 소켓 · 프로세스 · 디스크"]
    F --> G["7 · 전 플랫폼 CI<br/>실제 실행 · skip/delete 검사"]
    G --> H["8 · 안전성<br/>Miri · sanitizer · unsafe 감사"]
    H --> I["9 · 비기능<br/>성능 · 메모리 · 바이너리 크기"]
    I --> J["10 · canary · 롤백 리허설"]
```

각 칸은 앞 단계가 통과해야 다음으로 넘어가는 게이트다. 실패를 주석, 스텁, 테스트 건너뛰기, 진단 억제로 숨긴 변경은
통과로 세지 않는다.

## 6. 권장 공유 상태와 쓰기 권한

```mermaid
flowchart TB
    subgraph Immutable["작업자가 읽는 불변 입력"]
        R["실행 명세 (run manifest)"]
        P["PORTING.md"]
        L["LIFETIMES.tsv"]
        Q["epoch 작업 명세"]
        B["기준선 · 테스트 무결성"]
    end

    subgraph Worker["병렬 작업자"]
        W1["구현자"]
        W2["리뷰어 A"]
        W3["리뷰어 B"]
        W4["수정자"]
    end

    subgraph Control["역할별 서비스가 기록하는 공유 제어 상태"]
        S["작업 임대 · 작업 상태<br/>스케줄러"]
        E["증거 원장<br/>증거 기록기"]
        C["기준 검증 결과<br/>검증자"]
    end

    subgraph IntegratorOnly["통합자만 바꾸는 Git 상태"]
        I["통합 브랜치"]
    end

    Immutable --> Worker
    Worker --> X["패치 · 리뷰 보고서 · 증거"]
    X --> S
    X --> E
    S --> I
    I --> C
    C --> E
```

권장 설계가 작업자의 `git reset`, stash, 공용 브랜치 commit, 전역 build를 막는 이유는 병렬 실행에서도 같은 입력으로
재현 가능한 통합 결과를 얻기 위해서다. Bun도
초기에 같은 저장소에서 `stash`, `stash pop`, `reset --hard`를 병렬 실행하다가 변경을 잃었다. 다만 공개 workflow의
git·추가 파일 정책은 단계마다 달랐다. 통합자 전용 쓰기 권한은 integration ref에만 적용한다. 작업 상태, 증거, 검증
결과는 각각 스케줄러, 증거 기록기, 검증자가 전용 API로 기록한다. 이 권한 분리는 Bun이 전 단계에서 사용했다고 확인된
사실이 아니라 공개 workflow의 편차를 없애기 위한 보완책이다.
