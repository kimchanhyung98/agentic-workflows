# 설계 원칙

AI 워크플로우 시스템의 모든 설계와 구현 판단의 기준입니다. 이 원칙에 위배되는 구현은 허용하지 않습니다.

---

## 원칙 요약

| 원칙 | 핵심 질문 |
|------|----------|
| C1 관찰/판단 분리 | 사실 수집과 판단이 같은 단계에서 이루어지는가? |
| C2 계약 기반 범위 | 범위가 구조화된 계약으로 고정되어 있는가? |
| C3 결정론적 Gate 우선 | 기계가 검증 가능한 것을 AI에 위임하고 있는가? |
| C4 다중 관점 | 한 곳만 보고 결론을 내리고 있는가? |
| C5 위험 비례 투자 | 모든 작업에 동일한 파이프라인을 적용하고 있는가? |
| C6 상태 외부화 | 상태가 LLM 컨텍스트에 보관되고 있는가? |
| C7 역할 분리 | 한 역할이 계획, 실행, 검증을 모두 하고 있는가? |
| C8 구조화된 피드백 | 실패 피드백이 자유 텍스트로만 전달되는가? |
| C9 재현 후 확정 | 코드 분석만으로 수정을 확정하고 있는가? |
| C10 산출물 교체 | 목적마다 별도 파이프라인을 만들고 있는가? |
| C11 세션 분리 | 장기 세션이 문맥을 오염시키고 있는가? |
| Spec-as-Truth | 동작을 바꾸려면 코드를 수정해야 하는가? |
| State Externalization | 세션이 끊기면 작업을 이어갈 수 있는가? |
| Tool Neutrality | 다른 AI 도구로 교체할 수 있는가? |

---

## C1. 관찰과 판단을 분리한다

**정의**: 코드에서 보이는 사실(observation)과 그 사실에 대한 판단(judgment)은 서로 다른 단계에서, 서로 다른 역할이 수행합니다.

- 관찰: 엔드포인트 존재, 테이블 참조, import 의존성 — 심각도 없이 사실만 기록
- 판단: 심각도 판정, 결론 도출, 권장 사항 — 관찰 결과를 입력으로 받아 수행

**근거**: 관찰과 판단이 뒤섞이면 확증 편향이 발생합니다. "이슈가 있다"고 먼저 판단하면 증거를 선택적으로 수집합니다. 사실을 먼저 모으고 나중에 판단해야 누락이 줄어듭니다.

**위반 신호**: observation에 심각도(High, Critical)가 포함됩니다. 프롬프트가 "이슈를 찾아라"로 시작합니다.

---

## C2. 계약으로 범위를 고정한다

**정의**: 실행 전에 범위(scope)를 구조화된 계약으로 명시하고, 실행 중/후에 계약 준수를 강제합니다. 자유 형식 텍스트는 계약이 아닙니다.

- plan-contract: allowed_files, forbidden_paths, requirements, test_requirements
- Writer/Judge 스키마: claim, evidence, source_files, confidence

**근거**: 범위가 텍스트로만 존재하면 사후 검출만 가능하고, 위반이 누적된 후에야 발견됩니다. 구조화된 계약은 기계적 검증(diff 가 allowed_files의 부분 집합인지)을 가능하게 합니다.

**위반 신호**: 구현이 plan에 없는 파일을 수정했는데 verify까지 모르고 있습니다. Writer 출력에 evidence 없이 claim만 존재합니다.

---

## C3. 기계가 잡을 수 있는 것은 기계가 잡는다

**정의**: 결정론적으로 검증 가능한 것(lint, typecheck, test, scope diff)은 도구 실행으로 확인하고, AI 리뷰에 위임하지 않습니다.

- 결정론적 gate: format, lint, typecheck, test. 모두 통과해야 AI 리뷰에 진입
- scope gate: changed_files가 allowed_files의 부분 집합인지 확인. 위반 즉시 차단
- gate 미정의 시: skip하되 "결정론적 검증 미실행" 경고를 기록하고 change class를 보수적으로 승격

**근거**: AI에게 lint 오류를 분석하게 하는 것은 비용 낭비이자 불확실성 추가입니다. 도구가 확정적으로 판별하는 영역은 도구에게 맡기고, AI는 설계 적절성, 비즈니스 로직, 보안 패턴에 집중합니다.

**위반 신호**: gate가 정의되어 있는데 verify가 이를 실행하지 않습니다. gate 결과를 AI 판단으로 override합니다.

---

## C4. 한 곳만 보면 틀린다

**정의**: 모든 분석과 수정은 관련된 모든 코드 경로를 확인한 후에 결론을 내립니다. 서버만, 한 파일만, 한 관점만 보고 결론 내리지 않습니다.

- Writer 병렬: 최소 2개 이상의 관점(구조/행위, 보안/품질/성능)으로 동시 분석
- Code Path Inventory: 같은 기능을 건드리는 모든 경로를 사전에 식별

**근거**: "한 곳만 보고 PR을 올린 후 폐기"하는 패턴이 반복됩니다. 서버 코드만 보고 수정했으나 실제 원인이 클라이언트, 다른 코드 경로에 있는 경우입니다.

**위반 신호**: 한 파일만 읽고 결론을 내립니다. 문서화/리뷰 모드에서 Writer가 1개뿐입니다.

---

## C5. 위험도에 비례하여 투자한다

**정의**: 모든 작업에 동일한 파이프라인을 적용하지 않습니다. change class에 따라 review depth, 승인 경로, 격리 수준, gate 범위를 차등 적용합니다.

| 등급 | review depth | 승인 | 격리 | gate 범위 |
|------|-------------|------|------|----------|
| small | gate만 | auto 가능 | local | 변경 파일만 |
| standard | gate + AI 리뷰 | auto 조건부 | worktree | 변경 먼저 → 전체 |
| high-risk | gate + AI 리뷰 다수 + 사람 | 사람 필수 | isolated worktree | 전체 |

**근거**: 문서 오타 수정에 전체 파이프라인을 돌리면 낭비이고, 인증 리팩토링을 자동 승인하면 위험합니다. 리소스(시간, 토큰, 사람의 주의)는 유한하며, 위험도에 비례하여 배분해야 합니다.

**위반 신호**: small 작업이 전체 단계를 거칩니다. high-risk 작업이 자동 승인됩니다.

---

## C6. 상태는 파일에 둔다

**정의**: 모든 실행 상태와 단계 간 전달 데이터는 파일 시스템에 외부화합니다. LLM 대화 이력에 상태를 보관하지 않습니다.

**근거**: (1) LLM 세션은 휘발성입니다. 컨텍스트 압축, 세션 종료, Provider 교체로 상태가 사라집니다. (2) 파일 기반이면 어떤 LLM이든 같은 상태를 읽을 수 있습니다. (3) git으로 버전 관리, diff로 변경 추적이 가능합니다.

**위반 신호**: Phase 전환 시 이전 결과를 대화 이력에서 참조합니다. 세션을 끊으면 작업을 이어갈 수 없습니다.

---

## C7. 역할을 분리하고 권한을 제한한다

**정의**: 하나의 역할이 계획, 실행, 검증을 모두 하지 않습니다. 각 역할은 명시된 권한만 가집니다.

| 역할 | 할 수 있는 것 | 할 수 없는 것 |
|------|-------------|-------------|
| Orchestrator | 상태 관리, 라우팅, Phase 전환 | 코드 수정, AI 호출 |
| Executor | allowed_files 내 코드 수정 | forbidden_paths 접근, plan 변경 |
| Reviewer | 관점별 분석, claim 생성 | 코드 수정, 최종 판정 |
| Judge | claim 선별/병합, 일관성 검증 | evidence 수정, 새 claim 생성 |
| Gate | 도구 실행, pass/fail 판정 | AI 판단, 예외 허용 |

**근거**: 같은 모델이 계획하고 실행하고 검증하면 자기 검증 편향이 발생합니다. 역할 분리는 이 편향을 구조적으로 차단합니다.

**위반 신호**: 구현 Phase가 자기 코드를 검증합니다. Judge가 Writer의 evidence를 수정합니다.

---

## C8. 피드백은 구조화하고, 재시도는 예산 내에서 한다

**정의**: 실패 시 severity, location, suggestion이 명시된 구조화된 피드백을 생성하고, 재시도 횟수에 예산을 둡니다.

- 피드백 구조: severity, location(file:line), category, description, suggestion
- 재시도 예산: 총 시도 횟수 상한, 같은 카테고리 반복 상한
- 같은 카테고리가 반복되면 자동 수정을 포기하고 에스컬레이션

**근거**: 비구조적 피드백은 재시도 시 같은 실수를 반복하게 합니다. 구조화하면 자동 수정이 정확해지고, 예산 없는 재시도는 비용을 폭발시킵니다.

**위반 신호**: 피드백이 자유 텍스트로만 전달됩니다. 재시도 횟수에 상한이 없습니다.

---

## C9. 재현 전에 확정하지 않는다

**정의**: 코드 분석 결과만으로 수정을 확정하지 않습니다. 가능한 범위 내에서 재현(또는 동등한 검증)을 거친 후 확정합니다.

- 검증 수준 기록: 코드 분석만 / 유닛 테스트 / 통합 테스트 / 스테이징 재현 / 프로덕션 데이터 확인
- 에이전트 결과도 검증 대상: LLM이 결론을 내려도 재현 없이 신뢰하지 않습니다

**근거**: "코드 분석만으로 원인을 확정하고 수정에 들어간" 패턴이 PR 폐기의 주요 원인입니다. 에이전트 분석도 확증 편향에 취약하며, 재현이 유일한 교정 장치입니다.

**위반 신호**: investigation 없이 바로 구현에 진입합니다. verification_level이 기록되지 않습니다.

---

## C10. 산출물은 목적에 따라 교체한다

**정의**: 공통 기반 계층은 유지하고, 목적(mode)에 따라 Writer/Judge 구성과 산출물을 교체합니다.

| 목적 | Writer 구성 | 산출물 |
|------|------------|--------|
| 문서화 | Writer 2개(구조+행위) → Judge | 구조화된 문서 |
| 리뷰 | Writer 3개(보안+품질+성능) → Judge | 리뷰 리포트 |
| 조사 | 단일 Writer(코드 접근 권한) | 조사 리포트 |

**근거**: 목적마다 별도 파이프라인을 만들면 코드가 폭증하고, 공통 계층의 개선이 모든 목적에 전파되지 않습니다. 공통 기반 + 교체 가능한 끝단이 유지보수와 확장에 유리합니다.

**위반 신호**: 리뷰 모드용 계층을 별도로 구현합니다. 새 목적 추가 시 처음부터 복사합니다.

---

## C11. 세션은 작업 단위에 맞게 분리한다

**정의**: 같은 목표와 강한 의존성을 가진 작업은 같은 세션에 두되, 목표/도메인/작업 모드가 바뀌면 새 세션 또는 워커 분리를 우선 검토합니다.

- 오케스트레이터 책임: 전역 목표, 상태, 계약, 세션 연속성 판단 유지
- 워커 입력: 전체 히스토리 대신 목표, 현재 상태, 핵심 제약, 참조 아티팩트 우선 전달
- 판단 기준: 토큰 절감만이 아니라 재브리핑 비용, 문맥 오염, 재작업 가능성을 함께 고려

**근거**: 긴 세션을 무조건 유지하면 과거 합의가 현재 작업을 오염시킵니다. 반대로 과도하게 분리하면 재브리핑 비용과 누락 위험이 커집니다.

**위반 신호**: 작업 모드가 바뀌었는데 이전 세션을 끌고 갑니다. 워커에게 전체 히스토리를 그대로 넘깁니다.

---

## Spec-as-Truth (명세가 진실 공급원)

**정의**: 명세 파일이 시스템 동작의 유일한 진실 공급원입니다. 코드는 오케스트레이션만 담당하고, AI의 동작을 결정하는 것은 명세 파일입니다.

- 명세(spec): 프롬프트, 프로토콜, agent card — AI가 **무엇을** 하는지 정의
- 코드(code): loader, orchestrator, runner — **어떻게** 실행하는지 정의
- 명세를 편집하면 코드 수정 없이 동작이 바뀝니다

| 변경 유형 | 수정 대상 |
|----------|----------|
| 오케스트레이션 로직 | 코드 |
| AI 프롬프트 내용/형식 | 명세 |
| Gate 조건, artifact 목록 | 계약 |

**근거**: 프롬프트가 코드에 하드코딩되면 동작 변경마다 코드 배포가 필요합니다.

**위반 신호**: 프롬프트가 코드 파일에 하드코딩되어 있습니다. 동작 변경에 코드 배포가 필요합니다.

---

## State Externalization (상태 외부화)

**정의**: 모든 실행 상태와 단계 간 전달 데이터는 파일 시스템에 외부화합니다.

| 능력 | LLM 컨텍스트 의존 시 |
|------|------------------|
| Provider 전환 | 불가능 (대화 이력 소실) |
| 세션 재개 | 불가능 (컨텍스트 리셋) |
| 감사 추적 | 제한적 |
| 병렬 실행 | 불가능 (세션 격리) |

**근거**: 상태 전이는 원자적 rename 패턴을 사용합니다. 임시 파일에 먼저 쓰고, 완료 후 원본을 교체합니다.

**위반 신호**: Phase 결과를 LLM 대화 이력에서 참조합니다. 상태 파일 없이 파이프라인을 실행합니다.

---

## Tool Neutrality (도구 중립)

**정의**: 같은 명세가 어떤 AI CLI 도구에서든 동작합니다. 특정 도구의 전용 문법, API, 호출 규약에 종속되지 않습니다.

- 중립: 명세, 상태, 계약 — 도구 전용 문법 없음
- 흡수: Provider 계층이 도구별 차이를 흡수

**달성 전략**:
1. 프롬프트에 도구 전용 문법을 사용하지 않습니다
2. 상태 형식은 JSON/markdown만 사용합니다
3. 도구별 차이는 Provider 계층에서 흡수합니다
4. 새 도구 지원은 Provider 구현 추가만으로 가능합니다

**위반 신호**: 프롬프트에 특정 도구의 전용 태그가 포함되어 있습니다. 특정 도구에서만 파이프라인 실행이 가능합니다.

---

## 적용 우선순위

원칙 간 충돌 시 다음 순서로 우선합니다.

| 순위 | 원칙 | 근거 |
|------|------|------|
| 1 | C9 재현 전에 확정하지 않는다 | 검증 없는 결과물은 무의미 |
| 2 | C1 관찰과 판단을 분리한다 | 나머지 원칙의 전제 |
| 3 | C2 계약으로 범위를 고정한다 | 범위 없는 실행은 제어 불가 |
| 4 | C3 기계가 잡을 수 있는 것은 기계가 잡는다 | 비용 효율의 기본 |
| 5 | C7 역할을 분리하고 권한을 제한한다 | 편향 방지 |
| 6 | C4 한 곳만 보면 틀린다 | 품질 |
| 7 | C8 피드백은 구조화하고 재시도는 예산 내에서 | 효율 |
| 8 | C5 위험도에 비례하여 투자한다 | 효율 |
| 9 | C6 상태는 파일에 둔다 | 인프라 |
| 10 | C11 세션은 작업 단위에 맞게 분리한다 | 운영 효율 |
| 11 | C10 산출물은 목적에 따라 교체한다 | 확장성 |

## 원칙 간 상호작용

4개 설계 원칙은 상호 강화합니다.

- Spec-as-Truth → Tool Neutrality: 명세를 markdown으로 작성하면 도구 중립 달성
- State Externalization → Tool Neutrality: 상태를 파일로 외부화하면 어떤 도구든 읽기 가능
- Tool Neutrality → Provider Pluggability: 도구에 독립적이면 Provider를 자유롭게 교체
- Provider Pluggability → Spec-as-Truth: Provider가 바뀌어도 명세는 유지
